Excel 转 PDF「一次成功一次失败」：一次连环事故的完整复盘

2026-11-20
编程 / LibreOffice
字数统计: 6.9k   |   阅读时长≈ 28 分钟

一个 Java 服务调用 LibreOffice 把 Excel 转成 PDF，出现了最让人抓狂的症状：同一个文件，第一次成功，第二次失败，第三次成功，第四次又失败，严格交替。等登上机器排查才发现，事情远比"转 PDF 挂了"复杂——两个跑歪的进程、一个选错的容器底座，再加一个随时可能把机器带走的 Swap 危机。

一、症状：一半成功，一半失败

业务方的反馈很具体：同一个 Excel 文件，转换结果严格交替——成、败、成、败。

这种"部分可用"比彻底挂掉更麻烦。彻底挂了，监控立刻报警；一半成功，端口探活永远是绿的，监控却永远不响，只有业务方在关键流程里一次次撞上那次失败。

当时服务侧是 external 模式，连宿主机上手起的 LibreOffice：

表面一切正常，端口在监听、进程在跑。没人知道，这台机器上的 soffice 已经"跑歪"很久了。

二、上机：三板斧，以及它们能看到什么

登上 host-172-18-100-52（CentOS，up 668 days，连续运行快两年），用 ps / netstat / pmap+top 现场把脉。

2.1 ps：两个"半瘫痪"的进程

进程 端口 %CPU RSS TIME（累计 CPU） 启动 关键差异
3101751 8191（仅本机） 0.0% ~3 MB 0:00.78 2025 带 -env:UserInstallation=/tmp/...port-8191_...
4168552 8199（对全网） 65.4%（均值） ~44 MB 208953:34（约 145 天） 2025 完全没有 -env:UserInstallation

三条可以直接确认的事实：

  1. 8199 进程的启动行缺失 -env:UserInstallation，因此它必然回落到默认配置目录 /home/appadmin/.config/libreoffice。
  2. 8191 进程另有独立配置目录，压根不碰默认目录——这两个进程不在同一个"房间"里。
  3. 8191 进程累计 CPU 只有 0.78 秒，说明它自 2025 年被拉起后从未真正处理过一个任务，是个没人用的空壳。

顺带纠一个容易说错的词：3101751 的状态是 Sl（sleeping + 多线程），top 也明写 0 zombie。它不是僵尸进程——僵尸（Z 态）已经终止、只剩进程表项、RSS 为 0。准确说法是空壳进程。

这里有个口径陷阱，当时差点被它骗了：ps aux 的 %CPU 是生命周期均值（累计 CPU ÷ 存活时长），top 的 %CPU 是瞬时值，两个不能混着用。而这批数据里三者互相打架：

  • 按 %CPU 65.4% × 668 天推算，累计 CPU 该有 437 天；
  • 按 2025 年内启动（存活最多 365 天）推算，也该有 240 天；
  • 而 TIME 实际只有 145 天。

三种算法差一倍以上，说明 %CPU / TIME / START 至少有一项口径不可靠。所以后面的判断只做定性——“长期吃满一个核，累计消耗上百天”——不做定量换算。

2.2 netstat：电话拨得通，对面不吭声

netstat 能证实的只有两件事：端口在监听、监听队列没有积压。它证明不了"业务处理层坏了"，也证明不了"请求一定能建立 TCP 连接"——那得看 ESTABLISHED 连接数。

  • Recv-Q / Send-Q 都是 0 → 没有排队连接，不是被网络拥堵卡住；
  • 端口 LISTEN → 客户端不会报 Connection refused；
  • 8199 绑定 0.0.0.0（对全网开放，本身就是隐患），8191 绑定 127.0.0.1（仅本机）。

最阴险的地方在这儿：电话拨得通，对面是台只会嗡嗡响的机器。客户端把"请把 Excel 转成 PDF"发过去，对面收了却永远不开始转，一路空转 CPU，直到客户端 TimeoutException。

打个比方，你打客服电话，线路一切正常（netstat 绿），对面接起来只"嗡嗡"响不吭声（CPU 空转、无响应），最后电话自己挂断（超时）。

而这一步最该做却没做的，是抓一次 strace -f -p 4168552、看一眼 /proc/4168552/wchan——那才能真正区分"它在等锁"和"它在用户态空跑"。缺了这一步，后面关于"死锁"的所有说法只能停在猜测。

2.3 pmap + top：不是内存泄漏，但系统站在悬崖边上

第一层：不是内存泄漏。 pmap -x 汇总行的三列是 VIRT / RSS / Dirty，831872 / 50816 / 38272（kB）——两个进程实际常驻物理内存共约 49.6 MB，不到系统 1%。"内存泄漏"可以彻底排除。

第二层：Swap 已经被吃满。 MiB Swap: 19451.9 total, 0.4 free——只剩 400 KB。这里有个容易读错的地方：free 809.2 MB 和 avail Mem 4353.8 MB 不是一回事，后者包含可回收的 page cache。真实处境是空闲物理内存仅 809 MB，可回收后才 4.3 GB，而 Swap 已经归零——缓冲余地比数字看起来小得多。

再看 load average 4.95 配 65.5% id、13.5% wa：CPU 明明闲着大半，负载却接近 5，说明大量进程卡在等待 I/O，和 Swap 频繁换页高度吻合。

关于"高 CPU + S 态就是自旋锁死锁"——这个推论站不住。 三个理由：

  • 状态列来自单次采样瞬间。一个吃满单核的进程，恰好在两个 CPU 片之间进入可中断睡眠（S），完全正常，S 与高 CPU 并不互斥；
  • 真正的内核自旋锁表现是 R 态死占 CPU、拖住整核甚至触发 soft lockup，不会安静地待在 S 里；
  • 光看 S 和 %CPU，判断不出它在等什么。

所以能说的只有：4168552 在用户态或 UNO 桥接层长期空转、不响应请求；具体卡在锁等待还是事件循环忙等，没有取证，不能定论。

关于 OOM Killer 的误解：它不是"随机挑一个进程杀"。内核按 oom_score 挑人，通常优先杀内存占用最大的，所以最先死的多半是内存大户而不是 JODConverter；但当几个同规格的 Java 进程分数接近时，业务主进程被误伤的概率并不低。用"可能误伤、且不可预测"才准确。

现场结论：两个进程一个空转、一个空壳，业务上已经失效；但Swap 归零是优先级更高的事——此刻最该做的不是继续盯着 JODConverter，而是先降负载、再查谁吃光了 Swap。

三、为什么是"严格交替"？

这是整个事故里最有意思的问题，也是最容易归因错的地方。常见的解释有三种：

解释 内容 与数据的吻合度 疑点
A（最站得住） 请求在两条通路之间轮询：一条还能用，一条已经卡死在 8199，于是成功失败一替一次 ★★★★ "严格 50% 成功率"正是轮询的指纹 那个"还能用"的通路到底是谁，还需确认
B（常见说法） 进程被"污染"了，超时后重启，新进程干净所以下次成功 ★★ 能解释交替 逻辑上说不通：external 模式下 JODConverter 只做 UNO 客户端，不管进程生死，它连句柄都没有，靠什么"强制重启"宿主机上的进程？
C 两个实例配置不一致（一个 local 一个 external），恰好好坏各一 ★★★ 和 8191 那个 local 风格进程的存在很吻合 8191 是否真在对外服务还存疑（累计 CPU 仅 0.78 秒）

A 与 C 其实是同一件事的两个版本：结构都是"两条后端"，区别只在健康的那一半是谁。

关键推理很简单：如果只有一个后端、而它已经卡死，症状应该是 100% 失败，而不是交替。严格 50% 的成功率，天然指向"两条通路各占一半"。至于健康的另一半是 8191 上的进程，还是另一个应用实例——两条命令就能回答，但当时没查。

external 模式下的真实表现也印证了这点：超时不会触发任何回收动作，客户端只会报 TimeoutException，然后原样再连那个坏进程——结果是一直失败。所以"交替"不会是单实例里进程状态抖动造成的。

一句话：“严格交替"更像"轮询到两个质量不同的后端”，而不是"同一个进程时好时坏"。

四、三层根因，一个放大器

把这堆线索归拢，其实是三层问题叠加，外加一个纯系统级的风险放大器。

4.1 第一层：external 模式，进程生死没人管

external 模式的本质是：JODConverter 只当 UNO 客户端，宿主机上的 soffice 由谁起、起几个、跑多久、崩了怎么办，全凭人手。

在这种模式下，一个进程一旦进入异常状态（UNO 桥接卡死、转换器没释放文档、监听线程僵住），没有任何机制会回收它。它就一直占着端口、咬着 CPU，客户端每次连过去都是"连上了但不回话"。

8199 那个进程累计 CPU 145 天，却连一次成功转换的痕迹都没有——这正是该机制下的必然结果：不是它坏了，是没人管它。

4.2 第二层：改 local 模式，撞进 Alpine/musl 的墙

满以为改成 local + maxTasksPerProcess: 1 就万事大吉，结果"交替失败"变成了"每次都失败"。

原因在容器底座：local 模式让 JODConverter 在容器内部拉起 LibreOffice，而当时镜像是 Alpine Linux（musl libc），宿主机上的 soffice.bin 却是针对 glibc 编译的。Alpine 里没有 glibc 的 ELF 解释器（/lib64/ld-linux-x86-64.so.2），内核直接返回 ENOENT，于是执行 soffice.bin 报 not found。

这里有个坑：它报的是"文件不存在"，不是"权限不够"也不是"格式错误"。文件明明在那儿、权限也对，却报 not found，第一反应就该怀疑 libc，而不是去查路径。

之前 external 能用，是因为它连的是宿主机上手动起的进程（CentOS / glibc），绕开了容器里的 libc。

一句话：external 把 LibreOffice 留在 glibc 宿主机上跑，绕过了容器；local 把它拉进 musl 容器里，直接撞墙。

4.3 第三层：缺失的 -env，和那一把没人擦的锁

8199 进程的启动行里没有 -env:UserInstallation，于是它回落到默认配置目录 ~/.config/libreoffice。而那个目录里的 4/user/.lock，很可能是上一个同样没指定 -env 的进程留下的——进程早没了，锁还卡在那儿，于是它一直等一把永远不会释放的锁。

这里要纠正一个很容易犯的错：别把 8191 进程说成"和它抢锁"。8191 带着独立的 /tmp/.jodconverter_... 目录，它压根不碰默认目录。真正的对手是"历史残留"，不是另一个活着的进程。

证据强度也不够：手上只有启动参数这一条间接证据，既没有 ls -la 的锁文件快照，也没有等待栈。所以这一条只能算推断——但它衍生出的规范是硬的：每个进程必须绑定独立的 -env:UserInstallation，否则就是在默认目录里踩上一任留下的雷。

4.4 放大器：Swap 归零

必须把它单独拿出来说：Swap 耗尽和 JODConverter 失效没有因果关系——前者不会让 UNO 卡死，后者也造不出那 19 GB 占用。但它把整台机器的容错余量压到零，一旦触发 OOM，杀谁不可控。所以它处置优先级高于应用层修复，却不该被写成"根因"。

至于谁吃掉了 19 GB Swap：至今没查清。

4.5 三层归拢

层 内容 确定性 和"交替失败"的关系
一 external 模式进程生命周期无人管理，异常进程永久驻留 推断 直接相关：坏进程不会被回收
二 容器 musl 与宿主机 glibc 二进制不兼容 确定 解释"改 local 后 100% 失败"
三 缺失独立 -env + 默认目录残留锁 推断 解释"这个进程为什么烂"，不解释交替

五、处置：先止血，再换底座

顺序很关键——先降负载、再查 Swap、最后根治，绝不能只杀进程了事。

5.1 紧急止血

第 3 步的第二条命令值得单独说：ps aux --sort=-%mem 排的是 RSS，排不出谁占 Swap，用它找元凶是白找。要按 VmSwap 排序。

安全提示：生产环境不能立刻重启时，先用防火墙/安全组封掉 8199 入站，避免新请求继续加剧空转。另外 8199 长期绑 0.0.0.0 本身就是暴露面，根治时应改绑 127.0.0.1 或加白名单。

5.2 治本

  1. LibreOffice 改用 local 模式，配 maxTasksPerProcess: 1，每个任务后自动重启，从机制上切断状态累积。
  2. 服务从 Alpine 镜像换到 glibc 环境：非镜像启动（直接用宿主机二进制），或基础镜像换 Debian / Ubuntu，并补容器到宿主机的路径映射。

六、加固：哪些能加，哪些互斥

参数、探针、保活这三件事可以加，但有一条红线：别把两套进程生命周期管理叠在一起。

6.1 参数怎么算

两个常见公式是错的，先说清楚：

  • ❌ portNumbers ≈ CPU 核数 × 1.5，然后给 4 个端口示例——4 个端口对不上 ×1.5 的算法；
  • ❌ maxTasksPerProcess ≈ (总内存GB × 1024) / 单进程内存MB——这式子算出来的是"能开几个进程"，不是"每进程跑几个任务"，量纲就不对。按 32 GB / 300 MB 得 109，和常见的"填 20"也对不上。

正确口径是两条彼此独立的约束：

参数 由什么决定 怎么取
portNumbers（进程数 P） CPU 核数（转换是 CPU 密集型） P ≈ 核数 × 1~1.5，同时要满足 P × 单进程峰值内存 ≤ 可用内存 × 0.7，取较小值
maxTasksPerProcess 内存泄漏容忍度 压测出单任务内存增量 Δ，要求 基础占用 + Δ × N ≤ 单进程内存上限，留 50% 余量，工程上落 20~50
taskExecutionTimeout 最大文件转换时长 取 P99 × 3，生产 300000 起
taskQueueTimeout 并发排队容忍度 生产 60000

和本次处置的取舍：治污期用 1（每任务重启，代价是每请求多 13~16 秒冷启动）；稳态高吞吐按内存放宽到 20~50。两者不矛盾，但得知道自己在哪个阶段，别把治污参数当稳态参数发出去。

6.4 容器化的两个雷

  • musl / glibc 不兼容：本次第二层根因。基础镜像必须选 glibc 系（Debian / Ubuntu），或宿主机以非镜像方式启动 LibreOffice。口诀：soffice.bin 报 not found 而文件确实存在、权限也对，先怀疑 libc，别先查路径。
  • 中文字体缺失：转出来中文变方框。预装 fonts-wqy-zenhei、fonts-noto-cjk，避免运行时动态加载导致字体缓存异常膨胀。

七、三个还没答案的问题

复盘最忌讳"进程起来了就结案"，这次至少还留着三个扣：

  1. exit code 81 到底是什么。 日志里第一次启动就退了 81，被自动重试盖过去了。下一步该抓 VerboseProcess 转出的 soffice stderr，查 --accept 端口是否被占、/tmp 下的 profile 目录是否有残留，再对比第二次为什么能成功。
  2. 谁吃掉了 19 GB Swap。 至今没定位。得按 VmSwap 逐进程排查（数据库、ES、某个堆没设上限的 Java 应用），顺带看 vm.swappiness。
  3. "严格交替"的健康通路究竟是谁。 是 8191 上的进程，还是另一个应用实例？查一遍网关轮询配置、对齐成败日志的时间戳就能定，但当时没查，所以第三节只能给"最站得住"的解释，不能给定论。

另外还有两个小疑点：8199 为什么绑在 0.0.0.0；配置里 local.portNumbers 写的是 8190，而现场 8191 上那个进程带着 local 模式专有的 -env 目录——配置和现场对不上，说明中间发生过漂移，这个来历也值得查清。

最后一句实话：这次故障到底影响了多少请求、多少业务方，我手里没有完整数据，所以这篇只谈技术链，不谈损失量化。

八、几条教训

  1. "部分可用"比"彻底挂掉"更危险。 一半成功骗过了端口探活，监控全绿而业务在流血。要用业务成功率告警，不是 TCP 连通性。
  2. 先降系统风险，再修应用。 Swap 归零的优先级高于 JODConverter；OOM 按分挑人，被误伤的代价远大于一次转换失败。
  3. 三板斧能给"是什么"，给不了"为什么卡"。 区分"在等锁"和"在用户态空跑"必须靠 wchan / stack / strace；S 态配高 CPU，不能直接推成自旋锁。
  4. 进程生命周期要靠机制治，别靠祈祷。 local + maxTasksPerProcess 是机制，重启是手段，压测是依据。
  5. 容器底座的 libc 是隐形雷。 Alpine 跑不了 glibc 编译的 LibreOffice，not found 就是它的指纹。
  6. 每个进程都要有自己的 -env:UserInstallation。 默认配置目录是公共资源，谁回落到它，谁就在踩上一任留下的 .lock。
  7. 别把推测写成定论。 这次真正板上钉钉的只有三条：Swap 归零、没有内存泄漏、musl 不兼容。其余"进程污染"“争抢锁”"自旋死锁"都只是推断——写清楚证据到哪一步，比语气笃定更有说服力。
  8. 加固项之间会打架。 健康检查、进程保活、成功率告警要配套，但"local 模式 + systemd 常驻"这种组合只会制造新故障。
